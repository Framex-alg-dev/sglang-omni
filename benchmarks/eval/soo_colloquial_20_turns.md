## 执行矩阵与输入节奏

- 每个会话严格按 01–20 顺序执行一次，20 轮，不重复 20 次，也不为每条输入重建会话。
- 单会话一组、双会话一组：共 3 个独立会话、60 轮，每个双会话保留各自历史。
- 主套为音频＋图片；第 17 轮两帧，其余一帧，固定静态素材而非连续相机采样。
- 每会话 turn 开始间隔目标 6 秒；上轮超过 6 秒则等其结束，不重叠、不追赶。
- prompt 只用于生成录音；发送音频时禁止再发送同一份文字。记录录音 hash、图片 hash。
- 纯动作／纯表情轮预期没有音频：音频首包记 N/A，不能记成超时，也不能混进音频缺失率。
- 如另跑纯音频对照，视觉依赖轮 05–07、15–17 不能沿用图片答案断言，需单独版本，不能悄悄删图仍称等价测试。

素材准备可复用 `prepare_realtime_multimodal_user_journey.py`，传入本 JSON 的 `--cases`
和一个新的 `--output-dir`，避免覆盖既有 29 轮素材。场景均来自已有渲染器，音频需另行准备。

现有 `evaluate_realtime_multimodal_user_journey.py` 可加载本套 turns，且通过真实角色启动，
但它的 inter-turn-gap 是轮结束后的间隔，不是 6 秒 start-to-start，也没有本套双会话编排。
现有 latency 脚本则只支持单图和较简单断言，不能直接加载本套 turns。
因此不能直接运行旧脚本就宣称满足本套完整验收合同；后续执行需适配节奏、双会话及多帧。

## 判定和覆盖证据

JSON 的 expected_reply_groups、expected_action_candidates/categories、
expected_expression_candidates 是现有 journey runner 可识别的粗粒度检查。
manual_assertions 和 coverage_targets 是补充验收合同，**旧 runner 不执行这些字段**。
无硬编码候选的开放场景必须审阅回复和动作合理性；禁止动作、无音频、逐字朗读、
状态约束、事件先后也不能仅靠关键字检查判为通过。

每轮报告至少保存：输入源文本、素材 hash、实际回复、身体与表情完整结果、预期与实际对比、
失败原因、session/turn/trace ID、commit→动作／表情／文本／音频首包／turn.result 延迟。
另外保存数字人 Prompt 更新的接纳与生效确认，以区分返回事件和真正执行。

检查对应日志：共享意图结果与耗时、视觉范围、历史路由、类别评分是否跳过及原因、
Child 候选数、前缀缓存命中、候选调度继承、动作优先窗口释放原因、表现分支、
provisional reply 的保留／丢弃、TTS、独立 action 发布及 turn 汇总。
首次轮次与后续轮次分开标注；双会话统计不能掩盖某个会话的长尾。

“设计目标”不等于“分支覆盖”：第 12/19 轮若被快捷路径处理，类别评分覆盖仍为空缺；
第 18 轮也不保证触发 GPU 超时或内部异常。历史问题可验证上下文读取，不能单凭回答
正确就断言后台记忆提取任务已经运行。实际分支以服务日志为准。

以下不能靠口语句子可靠触发，单独测试，不能为追求覆盖而污染这 20 轮性能样本：

| 场景 | 测试手段与预期 |
| --- | --- |
| 取消／打断 | 回复中发 cancel，新轮启动；旧轮不得迟到输出或应用 Prompt |
| 第三会话 | 占满两个名额后发起第三个，验证 session_busy 与清理释放 |
| 预热失败／预算超限 | 隔离测试注入；验证启动失败与名额回收 |
| 动作优先窗口超时 | 人工延迟动作计算；验证上限后回复与表现放行 |
| 模型／TTS 失败 | 注入故障；验证降级、终态及等待方释放 |
| allowed/excluded、姿态约束 | 独立配置变体限制某候选，再发相应请求 |
| 重复、乱序、迟到事件 | D 端重放；验证去重、turn 所有权与动作间隔 |
| 主动／系统触发 | 本轮只覆盖用户触发，另建专门用例 |
