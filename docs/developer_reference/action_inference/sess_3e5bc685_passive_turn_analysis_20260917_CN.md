## 169 物理 batch 已生效

7 轮的 single 均为 169 个候选。深层 Thinker 调度日志显示，每轮候选都由一个
`request_count=169` 的物理 GPU batch 执行，属于该请求的成员数也是 169；没有再拆成
`[64,64,41]` 或 `[128,41]`。其中两轮在候选 batch 选中时另有 1 个请求等待，但候选
本身仍完整进入同一个 169 batch。

169 suffix 本身非常稳定，范围 223.0–241.7 ms，均值 235.5 ms。两个约 1.3 秒的
single 慢轮不是 169 batch 变慢，而是首次多模态/重连后只命中约 7k 公共前缀，额外
计算 6.5k–6.7k token，prefix prefill 增加到约 0.7 秒。后续 ASR 轮重新命中
12,845 token 后，single 回落到 743–756 ms。

两个 provider session 的用户前缀预热都成功：原 session 预热 684.1 ms，重连 session
预热 669.0 ms，均建立 12,423-token 的纯文本会话前缀。但带音频和多张图像的首轮使用了
不同的多模态上下文，仍需要单独建立更长前缀；因此仅做文本预热不能消除这部分冷启动。

## 结论

1. `max_running_requests=169` 已在真实会话生效，所有 single 都是单个 169 物理 batch，
   没有 OOM 或候选拆批。
2. 纯文本轮 single 已稳定在 604–634 ms；其中实际候选 suffix 约 223–235 ms，剩余时间
   主要是意图解析、预处理、前缀和调度。
3. 当前最大的动作延迟尖峰来自首次多模态上下文和重连后的前缀重建，而不是显存不足或
   169 batch。若继续降低单动作延迟，应优先预热/复用多模态 action prefix。
4. 应继续排查第 4 轮 WebSocket 为什么在动作就绪后断开，以及启用数字人 session worker，
   否则动作仍不会真正发送。
