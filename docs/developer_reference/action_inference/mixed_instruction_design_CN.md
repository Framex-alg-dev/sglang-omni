# 单轮语言、身体动作与表情复合指令方案

状态：设计评审稿，未实施、未进行模型或线上性能验证。
日期：2026-09-13。
评审基线：当前工作区源码，包括已有未提交修改；不是某个已部署版本。本文仅新增方案，不修改运行时代码。

## 1. 目标与建议

支持用户在一句话中同时要求语言内容、身体动作和表情。例如“说一比二”应回复“一”，执行目录中的 A259「数字二手势」；是否增加表情由当前表情策略决定。实际执行仍受会话候选范围、状态约束及输出模态限制。

建议先强化现有并行分支的共同语义规则与回归评测，不默认增加前置自由文本解析、ASR 或逐轮审核调用。需要区分两件事：共享规则可以减少分歧，但不等于各分支共享了一份解析结果，不能宣称提供确定性保证。若模型评测仍出现不可接受的分歧，再以受控实验评估统一解析。

本次方案固定在每轮一个身体动作、一个回复、一个表情的现有结构内优化；每个通道是否实际输出仍沿用现有策略，并非每轮强制三个通道都有输出。保留已有普通聊天、纯动作、纯表情、知识、历史、多模态和主动交互行为。时序、多动作和依赖执行结果的条件编排不在本次设计、实施或验收范围内，不为其增加解析字段、协议或推理调用。

| `reply/tts.py` 及交接文档 | 表现控制提供 TTS instruction；首个 append 需要 instruction | 表情/表现分支可能位于首音频关键路径，不能只优化身体动作耗时 |

源码路径均相对于 `sglang_omni/serve/realtime/`。动作语义公共规则另见 `sglang_omni/models/qwen3_omni/global_action_catalog.py`。

本次重点：一个回复、一个身体动作、一个表情应各自保持用户指定的语义；通道未指定时保留原有自然表达策略。动作支持判断和现有回复发布机制继续保留。

## 3. 语义契约

每个分支读取完整的当前输入，从中识别自己负责的任务，不能删掉其他部分后失去否定、条件、引用和执行者信息。

1. 一个句子可以有多个谓词和多个交付结果；没有标点、连接词或停顿，不代表只有一个任务。
2. “说一比二”按“说一／比二”理解；“说一比二这三个字”按朗读内容理解。前者不是某个固定字符串特判。
3. 用户要求说出的动作名称是语言内容，不自动构成执行请求；“说挥手”和“挥手说你好”必须区分。
4. 明确的语言、身体、表情目标分别保持原意。不得因“同意”把摇头改成点头，也不得因“一”把数字二手势改成数字一手势。
5. 不把否定、条件、第三方叙述或引用中的行为当作已授权的当前动作。“他让我挥手，你说你好”不自动授权当前角色挥手。
6. 只要求执行动作时，沿用纯动作回复规则。动作的目的不自动成为语言任务，例如“挥挥手逗我开心”。
7. 未指定动作/表情不等于禁止动作/表情；保留现有伴随、社交反馈、自我呈现和自然表情能力。明确禁止某个动作时，不得让伴随选择绕过禁止。
8. 语言原样输出要求优先于人设化扩写，正常内容与安全边界仍然适用；需要创作、解释、问答时继续正常生成。
9. 每轮最多选择一个身体动作和一个表情，并生成一个回复；不因识别出多个通道而增加动作数量或拆成多个回复。
10. 模糊音频需要结合声学证据和上下文；不能依赖音频中不存在的书面引号。若信息确实不足，允许最短澄清，不为所有复合指令增加澄清轮次。

### 3.1 预期用例

| 输入 | 回复 | 身体 | 表情/备注 |
|---|---|---|---|
| 说一比二 | 一 | A259 数字二手势 | 未指定 |
| 说二比一 | 二 | A258 数字一手势 | 未指定 |
| 摇头说同意 | 同意 | 摇头 | 不能做语义一致性“纠正” |
| 挥手介绍自己 | 根据人设介绍 | 挥手 | 语言是生成任务 |
| 笑着说一比二 | 一 | A259 | 明确微笑；视觉范围为 both |
| 笑着说你好 | 你好 | 无明确身体任务 | 视觉范围为 expression_only；仍需要语言 |
| 说一比二这三个字 | 一比二 | 无明确身体任务 | 保留正常伴随策略 |
| 挥手说别挥手 | 别挥手 | 挥手 | 后半是要求说出的内容 |
| 不要挥手，说你好 | 你好 | 禁止挥手 | 其他允许的伴随仍按规则 |
| 比二 | 沿用纯动作短回应/静默 | A259 | R2，无历史时 |
| 说刚才那个数字，比二 | 从语言历史解析数字 | A259 | 语言历史依赖，不能替代为动作历史 |
| 说一，做刚才那个动作 | 一 | 从动作锚点解析 | 动作指代，不扩大语言历史依赖 |

没有明确表情时，不将某个固定表情 ID 作为验收要求；没有明确身体任务时，也不统一强制 no_action。

## 4. 第一阶段实现方案

### 4.1 提示词组织

建立内部共用的简短语义规则构造模块，例如 `mixed_instruction_policy.py`，提供中英文版本。通用规则维护一份，各分支仅追加职责相关的小段。保持各分支现有不支持、历史、方向、状态和人设规则，避免重复拼接大段实例。

| 修改点 | 具体工作 |
|---|---|
| 路由主提示词和 S0/S1 消歧提示词 | 明确无连接词的多任务语义；“说一比二”属于语言需要；覆盖正反例 |
| 回复通用提示词 | 只完成语言任务；原样内容不加“好的”、动作描述或反问；一般问答仍正常生成 |
| 动作类别公共规则 | 明确身体目标优先；被引用的动作词不能触发；语言内容不得改写身体目标 |
| 身体 Child 提示词 | 保留原始请求中的身体目标、数量、左右、否定、对象；不以回复文本替换显式目标 |
| Performance 提示词 | `request_scope` 只描述视觉通道，与是否需要语言正交；出现语言不能冲淡 body 或 both |
| 各提示词覆盖机制 | 检查 runtime overrides 实际注入位置；保证部署使用的有效提示词包含新规则，避免只修改未生效默认值 |

不增加“mixed=true”这样的单一标签；它不足以表达具体任务，还可能导致后续错误地将所有多模态请求视为同一种情况。不把数字二手势 ID 写死在业务判断中；目录继续提供动作语义和映射。

### 4.2 运行时与故障路径

默认保持现有并发、provisional、TTS 和对外事件结构。先用测试确认下列不变量，发现缺陷时再以最小改动修复：

- R0/R1 的混合请求不会进入纯动作短回复路径。
- 类别不支持、Child 不支持、融合不支持不会错误丢弃独立语言回复。
- `expression_only` 不表示无语言；`both` 不表示语言+身体，而是身体+表情。
- 支持的身体动作选择不因回复完成、为空或生成失败而被自动替换为伴随；现有错误回退单独记录。
- 明确身体+表情仍保持现有原子失败策略，语言独立性另行处理。
- turn 取消后，不发送迟到动作或音频；promote/discard、终态和资源清理维持幂等。
- 单个 Turn 仍只交付当前协议允许的一个身体动作、一个回复和一个可选表情，不新增列表或执行计划字段。

对 Performance 误判导致身体取消的处理：先通过语义规则和模型测试修正，不默认给所有纯表情请求增加一次等待。只有真实评测表明早退错误仍显著，才实验性延迟高风险样本的身体取消。不能简单“等类别后再比对”：当前类别结果不携带显式意图证据，情绪伴随类别也不能证明用户要求身体动作；需要先设计可验证的冲突信号。

### 4.3 禁止作为首版捷径的做法

- 不对音频强制先 ASR 再把转写交给所有分支，避免增加串行耗时并丢失语气、重音等信息。
- 不用正则切“说X比Y”，避免伤害朗读、引用、否定、问答和非数字动作。
- 不从模型回复反推用户想做的动作；显式身体目标应来自用户输入。
- 不默认让语言任务、身体动作和表情分别再调用一次自由生成解析。
- 不对每轮追加一个生成式审核器，也不把 suffix 分差当作校准后的错误概率。
- 不用“文本里没有动作词”证明不存在动作指令，尤其不能对无转写音频这样判断。

## 5. 耗时分析与优化优先级

### 5.1 当前关键依赖

在开启路由/动作并行的配置下，逻辑结构近似如下；实际还受 GPU 准入和排队影响。

```text
当前音频/文本/图片
  ├─ 路由 R（可能追加消歧）─ 历史/知识等待 ─ 回复生成 ─ provisional 文本
  ├─ Category ─ Child ─ 身体结果
  │               ↑ 只有系统伴随路径需要实际回复前缀
  └─ Performance ─ 表情及 TTS instruction

provisional 文本 + instruction ─ TTS ─ 缓冲音频
融合与 promote ─ 正式文本/音频；动作按现有 ready 路径发布
```

显式身体动作的逻辑耗时近似 `Category + Child`；系统伴随路径还受到回复前缀等待影响。正式首字受回复首 token 与 promote 时刻共同约束，首音频还受 instruction、TTS 合成和释放缓冲影响。它们不是各分支平均耗时简单相加，也不等于只取最慢模型调用。

新增前置解析 I 后，如果后续必须等解析，原本可并行的 R、Category、Performance 至少新增一个 I 完成的依赖屏障；即使取代 R，也可能推迟本来先启动的 Category。与旧分支同时投机启动则增加 GPU 争用、取消成本和重复 Prefill，不能据“并行”推断免费。

### 5.2 优先级

1. **先不增加模型调用数。** 第一阶段仅调整有效提示词和必要的规则组织，维持显式身体动作不等回复前缀。
2. **控制提示词长度。** 共用短规则+少量最小对比样例；完整案例放评测集。报告各分支新增 token、Prefill、队列等待、路由消歧比例。
3. **保留缓存及调度。** 静态规则保持稳定、沿用现有缓存键契约；版本变化需要重新预热。媒体缓存命中不等于 Category/Child 的完整 KV 共享，不能重复计算收益。
4. **先测量再优化发布。** 分别记录回复生成和 promote 等待耗时。首版保持现有发布屏障；只有数据表明该等待是主要瓶颈，且能维持不支持处理、取消、文本和音频的一致性时，才单独实验提前发布。
5. **表情/TTS 单独量化。** 记录 instruction-ready 到首 append 的等待。若需要超时降级，另设显式策略，保证同一 Turn instruction 一致，并验证不会覆盖用户明确语气要求。

既有文档中的延迟数字属于历史环境，不能作为当前部署的实测基线。先锁定当前模型、硬件、提示词、候选目录及并发配置，跑同条件基线。

### 5.3 指标与初始准入建议

| 指标 | 测量要求 |
|---|---|
| 内部 TTFT / provisional 首字 / 正式首字 | 三者分开，以服务端 commit 为统一起点 |
| 首 PCM 就绪 / 首正式音频事件 / 客户端首次播放 | 分层记录；没有客户端埋点时不能称为用户首音耗时 |
| 身体 action.ready / expression.ready | 记录独立事件时间，不用 turn.result 代替 |
| R、消歧、Category、Child、Performance、TTS | 记录排队、执行、前缀等待和缓存状态 |
| 模型调用数、GPU 利用、吞吐、取消清理 | 验证新增提示词是否引发更多消歧和尾延迟 |

建议第一阶段以配对基线为准：正式首字、首音频与动作 ready 的 P50 回归不超过 5%，P95 不超过 10%；同步报告绝对毫秒变化。此为拟定工程门槛，不是性能承诺；已有更严格 SLO 时以其为准。P99、超时和取消错误单独报告，不能用平均数掩盖。近零耗时的强制主动路径使用绝对毫秒预算，不能套百分比。

按纯语言、纯动作、纯表情、混合、知识、历史、主动触发分别报告；冷启动与预热后分开；至少覆盖单会话、目标并发及压力负载。30 次只适合冒烟，不足以稳定判断 P95/P99；建议关键分组至少数百次，目标负载总体数千次，给出样本数与波动范围。

## 6. 第二阶段候选：共享 TurnIntent

只有第一阶段未达到语义验收且误差主要来自独立分支解释分歧时才进入。先离线对比；在线 shadow 如共享推理资源会干扰耗时，不能视为零成本。

结构仅围绕一个回复、一个身体动作、一个表情，表达“未指定、明确目标、禁止、指代和不确定”，不能只提供三个布尔值。示例为内部数据，不作为可信 system 指令执行：

```json
{
  "version": 1,
  "speech": {"kind": "verbatim", "content": "一", "history_required": false},
  "body": {"kind": "explicit", "target": "数字二手势", "constraints": [], "history_required": false},
  "expression": {"kind": "unspecified"},
  "ambiguity": "none"
}
```

种类包括 generated、prohibited、reference 等，不增加任务序列、通道时序或条件编排字段。模型解释结果和用户要求的文字属于有界数据，不能经字符串拼接升级为系统权限；原始媒体与必要上下文继续供后续分支使用。

历史依赖按通道标记；独立身体目标无需等待语言历史补全。解析器不决定动作支持、不直接执行 action_id、不绕过候选或状态校验。自由 JSON 需要约束解码、长度限制、schema 校验和超时策略；无效时回退现有分支一次，禁止无限重试或新旧结果双重发布。

实验比较：A=强化提示词的既有并行方案；B=解析替换部分路由再启动分支；C=有可靠触发信号时才解析。任何触发器本身的耗时、漏检与重复调用都计入成本。不要展开历史×语言×身体×表情的巨大标签笛卡尔积。未证明显著收益前，B/C 不作为默认生产路径。

原样回复也不立即采用文本硬提取直送 TTS：音频需要可靠内容恢复，且必须保持现有输出校验及取消契约。只有共享解析质量和收益验证后再单独评估绕过回复生成。

## 7. 测试与验收

### 7.1 三层验证

1. **代码/协议回归**：构造确定的分支结果，验证路由选择后的分支、unsupported 保留回复、both 原子性、早退取消、TTS 缓冲释放、打断与终态。此类测试不能证明模型理解正确。
2. **真实模型语义评测**：固定目录、人设、约束和模型参数，对真实文本及音频输入检查回复/动作/表情的联合正确性。不得仅检验 prompt 包含某句话。
3. **端到端性能与播放验证**：同条件 A/B、不同并发；测正式发布和实际播放，检查声音是否被截断、重复或丢失。

### 7.2 数据集

- 新增紧邻指令、语句排列变化、相反语义、引用、否定、第三方叙述和历史指代样本，均围绕一个身体动作、一个回复、一个表情；语句排列变化只用于验证语义提取，不验收执行先后。
- 音频包括无停顿/有停顿、不同语速与口音、轻噪声；书面引号样本不能代替语音消歧样本。
- 保留纯聊天、社交反馈、自我介绍、知识、图像问答、动作能力询问、声音表演、纯动作、纯表情、历史指代和主动触发。
- 覆盖候选支持/不支持、状态受限、模态开关、运行时提示词覆盖、路由失败和打断。
- “说一比二”测试需确认 A259 存在且允许；不允许时分别验收语言“一”与身体 unsupported，不能将其算成模型选错动作。

### 7.3 判定标准

- 原样语言以约定的标点容差比较，不能把额外“好的”“我来比二”归一化掉；TTS 检查实际读音，不能只看文本。
- 身体按明确请求和约束校验。方向未指定时允许有效等价候选；指定左右时不可放宽。无要求的表情不强制唯一 ID。
- 混合用例同时满足语言、身体、明确表情才算联合通过，分别报告各通道准确率及联合通过率。
- 建议核心固定案例多次运行全通过，广泛混合集联合正确率目标不低于 98%；旧能力分组不得出现关键语义回归，统计下降及不确定性必须披露。98% 为拟定目标，需配合样本数和置信区间，不能用极小数据集宣布达标。
- 输出前述性能指标与准入结果；准确率提高但超出既有 SLO 的版本不能直接替换默认版本。

## 8. 交付、灰度和回滚

第一批：有效提示词快照、语义规则补充、核心模型样本和旧能力基线。只实施规则强化和必要最小修复，不改变客户端协议。

第二批：完整模型评测、运行时故障回归、同负载延迟对比。交付包含失败样本、各分支决策、有效配置及版本的报告，避免只给总正确率。

第三批：按会话固定版本进行小流量灰度，保留旧规则开关；出现混合请求静默、显式动作被取消、禁止动作被执行或延迟超预算时回滚。规则版本切换按现有缓存策略重新预热，避免新旧提示词缓存混用。日志复用已有审计开关，不默认新增完整原始音频/文本落盘。

第四批（有证据才实施）：仅评估当前单动作、单回复、单表情结构下的统一解析与回复提前发布优化，分别评测与回滚，避免把多个变量合并到一次性能实验。

交付验收结果应明确：运行时代码是否修改、哪些配置实际启用、真实音频是否测试、客户端播放是否测量，以及三个通道各自与联合的正确率和延迟。本方案本身不代表任何推理正确率或耗时已经验证。
