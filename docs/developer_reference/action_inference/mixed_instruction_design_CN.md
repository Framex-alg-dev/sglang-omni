# 单动作、单回复、单表情：实现与验收

日期：2026-09-13。系统未上线，直接更新实现，不设旧版本兼容、灰度或双轨运行开关。原有工作区快照为 `6492932`。本次固定每轮最多一个身体动作、一个回复、一个表情；时序和多动作不在范围内。

## 1. 语义目标

| 输入 | 回复 | 身体 | 表情 |
|---|---|---|---|
| 说一比二 | 一 | 数字二手势 259 | 未指定 |
| 说二比一 | 二 | 数字一手势 258 | 未指定 |
| 笑着说一比二 | 一 | 259 | 微笑 |
| 摇头说同意 | 同意 | 摇头 | 未指定 |
| 挥手介绍自己 | 根据人设介绍 | 挥手 | 未指定 |
| 说一比二这三个字 | 一比二 | 未指定 | 未指定 |
| 笑着说你好 | 你好 | 无明确身体要求 | 微笑 |
| 不要挥手，说你好 | 你好 | 禁止挥手 | 未指定 |

未指定通道不是强制关闭。普通聊天、社交反馈、人设、纯动作短回应、知识、多模态与历史理解仍是功能要求。它们的测试属于功能正确性验证，不是上线兼容负担。

## 2. 最终架构

仅追加共用提示词的真实模型试验没有达到目标：回复、身体类别和表情范围仍可能对同一句话产生不同解释。因此使用一份共享的语义解析结果，而不是继续让所有分支独立拆句。

```text
当前用户文本/音频
  └─ 一次有界语义解析 TurnIntent
       ├─ 语言需要 + 历史需要 → 直接得到路由结果
       ├─ 原样说话 → 直接使用提取文字，流入现有文本/TTS发送流程
       │  生成任务 → 正常语言生成，附带解析数据与原始输入
       ├─ 身体目标 → 目录精确定位或类别评分 → 候选支持/状态校验
       └─ 表情目标 → 表现评分 → 表情与TTS instruction

需要语言时立即允许正文发布，无需等待身体评分；TTS仍等待本轮instruction。
最终结果等待各分支收尾，保证取消、错误、资源清理和终态一致。
```

### 2.1 共享解析

实现：`sglang_omni/serve/realtime/turn_intent.py`。

固定字段如下，不输出动作 ID、不直接判断动作是否受支持：

```json
{"body":"数字二手势","body_mode":"perform","face":"","speech":"verbatim","text":"一","history":false}
```

- `speech`：`verbatim`、`generated`、`none`。
- `text`：原样文字或语言任务；需要历史时保留指代，不猜测历史内容。
- `body_mode`：`perform`、`prohibit`、`none`，区分执行要求、禁止要求与未指定，禁止要求不应被标成要执行的身体动作。
- `body`：明确身体目标，保留否定、左右、物体等约束；没有则为空。
- `face`：明确表情目标；没有则为空。
- `history`：当前请求是否需要历史。

解析请求最多生成 256 token，等待上限 4 秒；严格校验键集合、枚举、类型、长度和原样内容非空。解析是模型生成后校验，不宣称底层支持 JSON 约束解码。解析失败、超时或服务异常只回退一次到正常路由；未完成请求中止并清理注册。用户取消继续传播，不当作普通失败吞掉。

成功解析替代 R0–R3 和可能的 S0/S1 消歧调用。主动触发、客户端提供的回复以及没有文本/音频的轮次不做这次解析。原始音频不经强制 ASR；解析请求直接携带当前音频，后续动作和回复仍保留必要的媒体与上下文。

### 2.2 语言输出

`verbatim` 且不需要历史时，直接把解析出的文字交给发送/TTS流程，标记为生成来源，不再做一次正文生成。这样“说一比二”不会被后续生成器重新扩写为比例解释或把动作读出来。

生成任务继续正常生成。解析结果作为用户上下文中的结构化数据传递，不拼接成新的 system 权限命令。系统提示词、人设边界、目录限制和状态约束不被解析数据覆盖。

有独立语言任务时，回复不因身体不支持而丢弃，也不等待身体候选完成才 promote。纯动作、主动触发及没有语言路由结果的路径继续依据自身的回复发布条件运行。

### 2.3 身体动作

实现：`action/category.py` 和公共语义提示词。

如果解析出的整个身体目标与目录的动作名称精确相等，且只对应一个动作 ID，就直接定位其当前可用类别，省去类别模型调用。随后仅让对应候选进入 Child 选择，继续检查状态、允许范围和不支持哨兵。若该类别下目标不可执行，不能用另一个手势冒充成功。

这是目录语义解析，不是对原始用户文本做“说X比Y”正则匹配。禁止子串匹配：例如“不要数字二手势”“左手数字二手势”不能在丢弃约束后直接匹配“数字二手势”。没有唯一精确目录匹配时，仍使用类别和候选评分。

未指定身体时仍可选正常伴随、社交反应；明确身体请求不得被回复内容覆盖。语言“一”不能把数字二改成数字一。

### 2.4 表情和通道融合

实现：`performance/pipeline.py`、`performance/fusion.py`。

表现候选的通道范围由共享解析直接确定：执行身体目标对应 `body_only` 或 `both`，未要求或禁止身体目标对应 `none` 或 `expression_only`。表现模型只在该范围内选表情，避免重新拆句导致分支互相覆盖；表情和说话是不同维度。

`expression_only` 表示只需要视觉表情，不表示无需语言。`both` 表示身体与表情，不表示语言与身体。明确要求身体和表情的组合继续使用原子失败规则；普通可选表情与明确表情分别处理。

## 3. 耗时与观测

新增解析不是免费操作，但替代了路由；原样回复同时省去正文生成，精确目录匹配还省去类别评分。生成类问答仍可能增加生成式解析成本，需要按任务类型统计，不能用原样短句收益代替整体性能结论。

正式首字不再等待身体结果。首音频还取决于表现分支和 TTS。增加的时序字段：

- `timing.intent_ms`：共享解析耗时。
- `timing.request_scope`：表现分支确定的视觉范围。
- `timing.reply.official_first_delta_after_commit_ms`：服务端首次发送正式文字的时刻。
- `timing.reply.promoted_after_commit_ms`：允许正式发布的时刻。
- 原有 `first_delta_after_commit_ms` 保留其生成/首个delta含义，不再混称正式首字。

解析成功与回退记录结构化事件。TTS已有 `instruct_wait_ms` 和首音频发送日志继续用于分解耗时。同轮TTS保持一个instruction，不中途更换。

共用提示词仍由 `utils/mixed_instruction_policy.py` 维护，覆盖主路由、消歧、有效回复规则、动作和表现。目录静态提示词参与现有hash/预热，不能把媒体缓存命中等同完整KV共享。扩大候选或更改提示词后必须重新测量。

## 4. 自动化评测

工具：`scripts/evaluate_mixed_instructions.py`。

```bash
.venv/bin/python scripts/evaluate_mixed_instructions.py \
  --url ws://127.0.0.1:18007/v1/session/realtime \
  --repeat 3 --warmup 2 --concurrency 1 \
  --output reports/mixed_text.json
```

默认使用 `tests/unit_test/fixtures/realtime_mixed_instruction_cases.json`。支持：

- 按用例独立会话，或用例内设置 `history` 前置轮次。
- `--case` 选择案例，`--repeat`、`--warmup`、`--concurrency` 设置负载。
- 用例 `audio` 指向相对用例JSON的单声道16kHz PCM16 WAV；有audio时只发送音频，不发送text转写。
- `--audio-output` 验证正式音频输出；`--session` 指定测试会话配置，如TTS音色。
- `excluded_candidate_ids` 构造不支持案例；生成任务的非空回复检查不等于内容质量人工验收。

每条结果保留通道检查、正式结果和事件时间摘要。原样回复仅容忍句末标点，不删除“好的”等额外内容。显式动作检查候选、execute和support_status；表情按明确要求检查，不强制可选表情唯一。超时/错误计入总样本分母，缺失延迟不填零。

脚本延迟以客户端发送commit到接收事件为准，包含网络与调度；不称为服务端计算耗时或真人听到声音的时刻。首PCM、客户端播放与实际读音仍应分别验证。

## 5. 测试范围与交付标准

代码回归覆盖解析校验、失败清理、共享解析替代路由、原样输出、目录精确定位、三个通道组合、不支持保留回复、TTS发布及取消。原有分支注入测试与解析测试分开，不能把注入模型结果当成理解正确率。

真实模型至少检查核心正例、朗读反例、相反语义、否定、普通聊天、纯动作、纯表情及不支持。合成语音单独标注，不能代表真人口音、噪声覆盖。测试报告中的低样本P95仅为本批观测，不宣称达到稳定的线上SLO。

完整结果记录在 `reports/mixed_instruction_implementation.md`；包含实际执行的命令、通过/失败样本及性能限制。本系统尚未上线，因此直接部署本地测试进程验证；不再增加旧规则开关或灰度流程。
