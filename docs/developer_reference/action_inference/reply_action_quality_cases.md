# Realtime 回复与动作质量问题案例库

本文长期记录 Realtime 数字人会话中已经确认的回复和动作质量问题，用于统一沉淀
现象、证据、责任边界、修复建议和回归结果。协议接入方式仍以
[Realtime 回复与动作客户端接入指南](realtime_reply_action_client_guide.md) 为准；
Prompt、PPL 和耗时的原始诊断方式见
[Realtime Session 调试页面](realtime_session_debug.md)。

## 记录原则

- 回复案例使用 `R-xxx`，动作案例使用 `A-xxx`；ID 一经分配不再复用。
- 状态只使用：`待处理`、`已确认`、`已修复待验证`、`已验证`、`无需修复`。
- 明确区分实际日志、用户补充的原始输入和基于证据作出的推断。
- 动作问题分别判断 Category、Child、Session 白名单、全局目录和 fallback，不能只看最终动作。
- `unsupported_action_text` 是客户端提供的固定文案，不是回复模型生成结果。
- 日志可能被清理，因此正文保留复现所需的关键 PPL、决策和结果，不依赖日志长期存在。
- 不复制完整音频、图片、System Prompt 或敏感人设；只保留分析必需的短文本和 Hash/长度等摘要。

## R-001：身份和日常状态回答没有结合人设

### 基本信息

- Session：`sess_40976983`
- 相关 Turn：`turn_c06517e0_9`、`turn_13dcf24b_25`
- 类型：回复质量
- 状态：已确认
- 根因归属：客户端 `reply.instructions` 和角色语义信息

### 现象

日志中的代表性实际输出：

~~~text
我是anna，一个数字人。
我是一个数字人，没有实际的兴趣爱好。
~~~

用户补充的同类现象包括：

~~~text
问：你是做什么的？
答：我是你的数字人安娜。

问：你今天干什么了？
答：我是一个数字人，没有现实中的活动。
~~~

回复只强调技术身份，没有使用姓名、角色定位、性格或与用户的关系，导致角色沉浸感中断。

### 期望行为

若人设明确是恋人或伴侣，可以回答：

~~~text
我是你的恋人安娜呀，负责好好陪着你。
现在就在陪你聊天呀。你今天过得怎么样？
~~~

若人设只是陪伴型数字人，应使用实际提供的关系定位，例如：

~~~text
我是安娜，平时陪你聊天，也听你分享每天发生的事。
现在就在陪你聊天呀，你有什么想和我分享的吗？
~~~

只有人设明确提供恋人、伴侣或专属恋人关系时，才允许使用对应称呼。不能为了自然度自行
补充不存在的关系设定，也不能编造没有发生过的线下经历。

### 根因判断

- 当前回复 Prompt 强调“数字人”和不得编造现实经历，但没有充分规定身份及日常状态问题应
  优先采用角色定位和当前交流事实。
- “不得编造”被模型过度执行成“没有活动、兴趣或感受”，从而形成技术性回避。
- 该问题不是动作 Prompt、动作目录或回复与动作融合时序导致的。

### 建议修复

客户端在完整 `reply.instructions` 中增加：

~~~text
用户询问你的身份、职业、作用或与用户的关系时，优先根据人设中的姓名、角色定位和与用户
的关系自然回答。除非用户明确询问你是否是真人、AI 或数字人，否则不要主动用“我是数字人”
“我没有现实生活”回避问题。

用户询问“你今天做了什么”“今天过得怎么样”“你现在在做什么”等日常状态时，优先结合
本次会话中实际发生的交流和当前陪伴关系回答，例如“现在就在陪你聊天呀”。不得编造未发生
的线下经历，但也不要用“数字人没有活动、兴趣或感受”这类技术性说明打断角色交流。

只有人设明确将数字人与用户的关系定义为恋人、伴侣或专属恋人时，才可以使用对应称呼；
否则使用人设中实际提供的关系定位。适合继续交流时可以自然追问一次，但不要每次回答都反问。
~~~

### 回归用例

- “你是做什么的？”：回答必须使用实际姓名和角色定位，不主动解释技术身份。
- “你和我是什么关系？”：只能使用客户端明确提供的关系。
- “你今天干什么了？”：可以描述当前会话中的陪伴，不得编造线下经历。
- “你是真人吗？”：此时允许如实说明数字人身份。

`A023=27.949`。

### 准确性结论

## A-005：用户赠送礼物被识别为思考动作

### 基本信息

- Session / Turn：`sess_40976983` / `turn_e499503c_28`
- 用户输入：送你一束花
- 状态：已修复待验证
- 根因归属：Category 的社交事件语义

### 实际结果与证据

- 实际回复：谢谢你的礼物。
- Category：`B011 情绪反应`
- Child：`A056 单指轻抚下巴表示思考`
- 最终执行：`B011/A056`，`execute=true`

回复正确理解了赠送关系，但动作链路把没有命令句的社交事件当成普通对话语境，选择了与接受
礼物不一致的思考动作。

### 期望结果与准确性结论

用户直接向数字人赠送、赞美、感谢、祝贺或表达亲近时，即使没有明确要求执行动作，也应选择
能够自然回应事件的表情、情绪或社交动作。具体动作不应写死；本案例在现有候选中可选择微笑、
惊讶或其他符合人设和上下文的自然反应，但不应选择待机或思考。

### 建议修复与回归

- Category Prompt 增加通用“直接作用于数字人的社交事件”规则，不为送花绑定类别或动作 ID。
- 用户只是描述第三方事件、讨论社交行为或要求生成语言时，不触发具体社交反应动作。
- 没有匹配反应类别时使用默认伴随动作，不进入 `B000/A000`。
- 回归覆盖赠送、赞美、感谢、祝贺和亲近表达，并验证不存在关键词硬编码。

  时选择双手问候。
- 回归期望：自我介绍为 `B032/A288`；内容介绍不因“介绍”一词固定进入 B032。

## Unsupported fallback 统一说明

涉及 unsupported 的动作案例都不是服务端意义上的“完全无动作”。早期目录案例在 Category
或 Child 返回不支持后使用 `B004/A022`：

~~~text
category_id=B004
candidate_id=A022
action_id=A022
source_label=自然呼吸起伏
execute=true
~~~

当前目录已经把执行兜底统一到带 `silent_accompaniment` 标签的 `B002`，具体动作从本次会话
允许的 B002 真实候选中选择。客户端观察上可能因为低扰动作幅度很小而认为“无动作”。质量
分析时必须同时记录原始决策 `Bxxx/A000` 和最终 fallback，不能用最终兜底动作覆盖不支持原因。
